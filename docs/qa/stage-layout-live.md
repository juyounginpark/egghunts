# 운영 스테이지 배치 확인 (2026-09-26)

사용자 요청에 따라 `node scripts/qa/stage-layout-live.mjs`로 GitHub Pages 클라이언트와 실제 EC2 방 응답을 비교했다. 임시 게스트 한 명으로 입장해 좌표만 조회한 뒤 퇴장·로그아웃했다. 이동, 알 획득, 기존 플레이어 저장 변경은 하지 않았다. 임시 게스트 프로필은 남아 있다.

## 확인된 원인

- 배포 클라이언트: `index-BruIB2YL.js`, `entrance:6,length:48,finalLength:225`.
- 운영 서버: `routeVersion:2`, 알 101개, 보스 21마리. 알·보스 데이터 자체는 존재한다.
- 2스테이지의 현재 화면 범위는 Z -54~-102이다. 서버의 알은 -123.8~-126, 보스는 -133으로 현재 화면의 3스테이지에 있다.
- 2~20스테이지 모두 서버가 보낸 소속 알·보스 좌표가 현재 클라이언트의 해당 지역 범위를 벗어난다. 20스테이지의 최종 알·보스도 포함된다. 1스테이지만 현재 범위 안에 남는다.
- 원인은 경로를 줄인 클라이언트와 이전 좌표를 사용하는 운영 서버의 배포 불일치다. 클라이언트에서 알을 새로 생성하거나 표시 좌표만 줄이면 서버의 획득·충돌 판정과 다시 어긋나므로 해결이 아니다.

## 로컬 구성 확인

현재 소스로 20개 지역을 생성했다. 모든 지역에 일반 알 5개·일반 보스 1마리·장애물 블록·환경 위험이 존재하고, 20지역에는 최종 알·보스가 추가된다. 2지역은 충돌용 장애물 블록 585개(개별 장애물 수가 아님), 태엽 기차 위험 1개이며 위험 위치는 Z -89이다.

기차의 대기 시각 표현은 선로 위주다. 실제 장애물 렌더링과 서버 공격 위치의 일치는 이번 API·정적 구성 조사로 확인하지 않았으며 브라우저·실기기 재현도 하지 않았다.

## 남은 조치

운영 서버에 현재 공통 엔진을 배포해야 한다. 현재 `runRoom`에는 저장된 방의 좌표를 routeVersion 3으로 변환하는 코드가 이미 있다. 새 방은 길이 48/225를 사용하며 기존 방은 입구 이후 깊이를 절반으로 변환한다. 저장 ID·소유·HP를 재생성하지 않는다.

이번 세션에서 서버 SSH 인증 수단은 확보하지 못했으며 운영 서버는 변경하지 않았다. 배포 후 같은 진단을 다시 실행하여 서버 routeVersion 3과 20개 지역 소속 범위를 확인하고, 2지역의 획득·추격·장애물 화면을 별도로 확인해야 한다. 전체 QA·빌드는 실행하지 않았다.
