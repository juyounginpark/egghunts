# 라이브 서비스 100~300명 준비

작성: 2026-09-30. 목표는 최대 동시접속 약 100~300명, 예산은 미정이다. 아래는 설계·산정 가정이며 수용 인원 보증이나 부하 테스트 결과가 아니다.

## 현재 장애와 제약

- 운영 조회에서 월 응답 payload는 10,737,414,798바이트로, 기본 10GiB 한도까지 3,442바이트 남아 있었다. 프로세스는 active, 재시작 0회, RSS가 아닌 systemd MemoryCurrent는 약 95MiB였고 디스크 사용률은 27%였다. 응답이 남은 한도보다 크면 요청은 503으로 실패한다. 작은 health 응답의 ready=true만으로 게임 입장 가능 여부를 판단할 수 없다.
- 운영 설정 GAME_MAX_ROOMS=4, 방당 5명이다. 서버는 t3.micro, 단일 Node 프로세스, CPUQuota=80%, MemoryMax=550M, V8 heap=384MB로 기록되어 있다.
- 정상 이동 갱신은 200ms 간격이다. 전원이 초당 5회 요청하면 100명은 500회/초, 300명은 1,500회/초다. 기존 전역 WebSocket 200회/초 상한을 넘는다. 명령·재연결 트래픽은 별도 여유가 필요하다.
- 인증 결과 캐시는 최대 10초, 원격 인증 조회는 초당 4회다. 만료 시각과 토큰 갱신에 따라 집중 요청이 발생할 수 있으며 지속 동접 100~300명에는 별도 검토가 필요하다.
- 방의 요청마다 모든 참가자의 GameState 복원·시뮬레이션·JSON 저장이 수행된다. 코어만 늘려도 단일 JS 프로세스의 실행이 코어 수만큼 병렬화되지는 않는다.

## 이번 구현

- sections-v2는 runtime.save와 runtime.fields의 각 속성을 별도 비교한다. 시간·재화가 바뀌어도 변하지 않은 몽글 보유 배열·펫 목록은 다시 보내지 않는다. 배열 자체가 변경되면 해당 배열은 전체 전송한다. world/peers/hazards 단위 추가 최적화는 측정 후 판단한다.
- 기존 v1/전체 응답을 유지하고 서버의 streamVersion 지원 응답 이후에만 v2를 요청한다. 연결·토큰·형식 변경 시 기준 상태를 초기화한다. 삭제된 속성은 remove 목록으로 제거한다.
- SQLite hot-path prepared statement를 재사용한다. 개인 JSON이 동일하면 profile revision과 클라우드 체크포인트를 늘리지 않는다. 동기 커밋과 WAL FULL은 유지한다.
- 1분마다 game-traffic 로그에 성공 응답 수·payload 바이트·현재 방/인원·월 누계를 기록한다. 월 한도 80%/95%에서 transfer-budget-warning을 기록한다. CloudWatch 등 알림 전달은 아직 구성하지 않았다.
- WebSocket 압축은 이번에 켜지 않았다. ws 공식 문서는 압축의 CPU·메모리 비용을 명시하므로 변경분 전송 이후 실제 분포를 먼저 확인한다. [ws 문서](https://github.com/websockets/ws#websocket-compression)

## 트래픽 산정

월 GB ≈ 평균 동접 × 사용자당 초당 응답 바이트 × 2,592,000 / 1,000,000,000 (30일).

아래는 **1인당 평균 2,000바이트/초라는 목표 가정**이다. 측정값이 아니다. 피크 동접을 월평균 동접으로 대입하지 않는다.

| 월평균 동접 | 월 게임 응답 payload |
| --- | --- |
| 10명 | 51.84GB |
| 30명 | 155.52GB |
| 100명 | 518.40GB |
| 300명 | 1,555.20GB |

예를 들어 피크 300명·월평균 30명이라면 표의 155.52GB 가정에 해당한다. TLS/HTTP/WS 헤더, 인증·DB·로그·에셋과 재접속 초기 스냅샷 등은 별도 반영해야 한다. 현재 게임 payload 한도와 실제 AWS 전송료는 동일하지 않다.

AWS는 여러 서비스·리전 합산 월 100GB 인터넷 송신 무료 범위를 안내한다. 다른 서비스 사용량에 따라 남은 범위가 다르며 이를 이 게임 전용 무료량으로 간주하지 않는다. [AWS EC2 요금](https://aws.amazon.com/ec2/pricing/on-demand/)

월 총비용은 서울 리전 Linux On-Demand 인스턴스 시간당 단가 × 약 730시간 + EBS/백업 + 공인 IPv4 + 인터넷 송신 + Supabase + 로그·모니터링으로 산정한다. 세금·환율은 별도다. 이번 조회에서 서울 개별 단가를 확정하지 못했으므로 금액을 임의로 기입하지 않는다.

## 서버 후보와 적용 순서

1. 현재 단일 소유자 구조를 유지하는 첫 비교 후보는 c7i.large(2 vCPU/4GiB)다. 자원 제한도 함께 검토하되 변경분 전송을 적용한 격리 환경에서 20→50→100명 순으로 검증한다. 사양만으로 100명 지원을 단정하지 않는다.
2. 300명 목표는 방 60개가 필요하다. c7i.xlarge(4 vCPU/8GiB) 또는 복수 호스트를 비교하되, 방을 소유할 프로세스·재접속 라우팅·저장소 소유권을 먼저 설계해야 한다. 현재 SQLite 파일과 동일 owner를 여러 프로세스가 동시에 공유하도록 단순 복제하지 않는다. 이 분산 구조는 아직 구현하지 않았다.
3. 인증 갱신, 전역/사용자/IP별 rate limit, nginx 연결, 소켓 수, DB 체크포인트량을 목표 요청률에 맞춰 함께 검증한다. 검증 전 운영 상한을 300명으로 풀지 않는다.
4. 일시 CPUQuota·MemoryMax 증가만으로 전체 최적화가 끝났다고 보고하지 않는다. 평균 및 P95/P99 응답 지연, 이벤트 루프 지연, DB 커밋 시간, 실제 트래픽, 오류·재연결, 장시간 RSS를 기록한다.
5. 서버 증설·유료 한도 변경은 사용자 승인 후 진행한다. 고정 HTTPS 주소, 백업과 복구, 상태/전송량 알림, 앱인토스 실제 인증·실기기 확인도 출시 전 남은 항목이다.

사양 출처: [AWS C7i 공식 사양](https://aws.amazon.com/ec2/instance-types/c7i/). 최신 서울 리전 가용성과 요금은 실제 적용 직전에 다시 확인한다.

## 검증·배포 상태

- 코드와 수동 회귀 검사만 추가했다. 자동 QA·빌드·성능 검사·운영 서버 배포는 실행하지 않았다. 실측 절감률과 최대 동접은 미확정이다.
- 수동 검사: `node scripts/qa/snapshot-delta.mjs`(Node 24+, 로컬 fixture), 서버 번들 생성 후 `node scripts/qa/ec2-host.mjs`(격리 fake Auth/DB). 사용자가 검증을 명시적으로 요청할 때 실행한다.
- 프런트만 먼저 올라가면 구 서버에서는 v1을 계속 쓴다. 최적화 효과를 얻으려면 새 서버 번들 배포도 필요하다. 서버 증설·월 한도 변경과 현재 한도 소진 장애 복구는 아직 수행하지 않았다.
