# 실제 방 이동 진단 — 2026-09-24

사용자가 실제 게임 진단 측정을 명시적으로 허용한 뒤 수행했다. 로컬 Vite의 현재 게임 코드에 읽기 전용 진단 훅을 메모리로 주입하고, 실제 Supabase 익명 인증과 방 API를 사용했다. `?qa=true`, 서버 모킹, 위치 강제 변경은 사용하지 않았다. 배포 사이트 자체의 브라우저 측정이나 휴대폰 측정은 아니다.

환경은 이 PC의 headless Edge, 390×844 viewport다. 정지 2.5초 → W+D 이동 5초 → 정지 1.8초 → S+A 이동 5초 → 정지 1.8초를 기록했다. JavaScript CPU 프로파일은 표본 추정치다. 네트워크 요청은 순차 진행되며 각 실행의 방/알 난수와 네트워크 상태는 다르다.

## 확인한 원인과 수정

- 첫 이동의 177ms 긴 작업이 `GameAudio.unlock`과 일치했다. 오디오 장치 초기화를 첫 로그인 클릭으로 이동해 플레이 도중 초기화하지 않도록 했다.
- `formatNumber`가 매번 `Intl.NumberFormat`을 생성했다. 소수점 자릿수별 포맷터를 재사용한다.
- 서버 응답을 받을 때 표시 오프셋을 빠르게 줄여 화면상의 걷기 속도가 출렁였다. 이동 중 보정 속도를 기본 이동 속도의 8%로 제한하고 예측용 지연 추정치를 완만하게 갱신한다. 충돌·피격·사망·권위 위치 확정은 유지한다.
- CORS 사전 요청에 600초 캐시를 허용했다. 서버의 인증·읽기·시뮬레이션·저장 시간은 민감 정보 없는 `Server-Timing` 헤더로 구분한다.

중간 재측정에서는 902.5ms의 왕복 95백분위와 116ms 긴 작업도 있었다. 최종 결과를 항상 보장되는 수치로 해석하지 않는다. 최초 실행의 별도 rAF 샘플은 렌더보다 한 프레임 먼저 수집돼 속도 비교에서 제외하고, 이후 렌더 직후 훅으로 측정한 `profiled`/`timing` 기록을 비교했다.

최종 서버 처리 시간 중앙값: 인증 44ms, DB 읽기 29.3ms, 게임 계산 9.6ms, 저장 34.6ms. 나머지 왕복/플랫폼/전송 시간 중앙값은 약 123.8ms였다. DB와 함수 모두 서울(`ap-northeast-2`)이며 자동 지역 선택과 서울 강제 호출 비교에서 유의미한 개선이 보이지 않아 리전 강제 지정은 추가하지 않았다. 지역 선택의 판단 근거는 [Supabase 지역별 호출 문서](https://supabase.com/docs/guides/functions/regional-invocation)다.

## 남은 한계

약 250ms 수준의 HTTP 왕복 지연은 남아 있다. 알 획득·타격 확정은 이 응답을 기다리며 위치 보정도 완전히 없어지지 않는다. 5명 동시 플레이·휴대폰·토스 실기기는 이번에 측정하지 않았다. 지속 연결과 서버 고정 틱으로 전환하는 작업은 이번 변경에 포함하지 않는다. 같은 문제의 추가 추정 수정 대신, 남은 증상은 요청별 시간 기록과 위치 오차를 기준으로 판단한다.

재실행: `node scripts/qa/live-movement.mjs <영문-보고서명>`. 새 게스트 계정이 생성되며 실제 서버 방을 사용한다. 원시 JSON/CPU 프로파일은 git에서 제외되는 `artifacts/performance/live-movement-*.json` 및 `*.cpuprofile`에 저장한다. 토큰·이메일·계정 ID는 보고서에 기록하지 않는다. `npm run qa:typecheck` 통과.
